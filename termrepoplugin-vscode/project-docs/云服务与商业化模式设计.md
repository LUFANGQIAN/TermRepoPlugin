# 云服务与商业化模式设计

## 一、文档目的

本文档用于明确 TermRepoPlugin 后续在以下几个方向上的产品与架构策略：

- 云服务是否要做，以及做什么
- 插件是否需要登录界面
- 如何在保持轻量化的前提下接入 AI 与云同步
- 如何兼顾开源、自建与商业化
- 网页端、移动端与 VS Code 插件之间如何形成统一体系

本文档的目标不是直接落实现，而是先把原则、模式和边界讲清楚，作为后续产品设计、接口设计和技术落地的依据。

## 二、背景与核心判断

### 1. 当前产品的核心价值

TermRepoPlugin 当前最打动人的地方，不是“能查词”，而是以下这些特质的组合：

- 本地优先
- 足够轻量
- 即装即用
- 不强依赖账号体系
- 没有明显的商业压迫感
- 非英语母语开发者也能低成本沉淀技术术语资产

这意味着：插件的产品气质本身就是竞争力。

### 2. 新需求带来的变化

后续希望加入的能力包括：

- 大模型自动分析单词、组合词和标识符
- 自动生成整体备注与拆词片段备注默认建议
- 云同步
- 后续网页端
- 后续移动端复习软件

这些能力天然会引入云服务，但如果处理不好，也会破坏当前插件的轻量感。

### 3. 核心判断

结论是：

- 云服务值得做
- AI 辅助功能很契合产品定位
- 插件不适合以“登录界面”为主入口
- 商业化应服务于“简化流程”，而不是“锁住用户”
- 本地可用、自建可行、托管可付费，应同时成立

## 三、产品原则

后续所有设计建议，都应尽量遵守以下原则。

### 1. 本地优先

插件在不联网、不登录、不配置任何云端服务的情况下，也必须保持核心功能可用：

- 收藏单词
- 管理本地词库
- 搜索与替换
- 导入导出

云服务只能是增强项，不能成为使用门槛。

### 2. 轻量优先 

插件端应尽量保持以下特征：

- 不引入复杂的首页登录流程
- 不增加沉重的账号中心感
- 不让用户在最开始就面对一堆服务配置
- 插件只做编辑器内高频必要交互

### 3. 开放优先

后续即便接入云服务，也应坚持：

- 所有协议公开
- 后端代码可开源
- 允许用户自建服务
- 官方托管与自建能力平权

### 4. 商业化克制

商业化不应建立在“封闭”和“限制基础能力”上，而应建立在：

- 官方托管更省事
- 官方服务更稳定
- 配置更简单
- AI 能力可直接用
- 多端同步体验更顺滑

简单说，收费是为了减少折腾，不是为了制造依赖。

## 四、用户分层

后续产品设计需要明确不同用户的需求差异。

### 1. 本地用户

特征：

- 不想登录
- 不关心同步
- 不一定愿意联网
- 只想安静地在本地管理术语

希望获得：

- 快速收藏
- 本地搜索复用
- 导入导出

### 2. 轻云用户

特征：

- 愿意使用 AI 建议
- 愿意偶尔同步
- 不愿意自己部署
- 但也不想体验很重的账号体系

希望获得：

- 一次配置后长期无感使用
- 收藏时自动生成默认备注
- 多设备词库同步

### 3. 极客 / 自建用户

特征：

- 愿意部署服务
- 对数据掌控有要求
- 可能希望自行接入模型供应商
- 可以接受填写 URL、Token、环境变量等配置

希望获得：

- 官方协议公开
- 自建足够简单
- 插件能接入自定义 endpoint

### 4. 托管付费用户

特征：

- 愿意付费
- 不愿意折腾
- 希望开箱即用
- 更在意“省时间”而不是“研究系统”

希望获得：

- 购买后快速激活
- 自动可用的 AI 与同步能力
- 尽可能少的配置成本

## 五、是否需要登录界面

### 1. 不建议把“登录”做成插件主入口

原因如下：

- 会明显增加 SaaS 感
- 会破坏工具的轻量气质
- 会让用户感觉“只是想记个单词，却先被要求进入系统”
- 与当前项目“本地优先”的精神不一致

### 2. 更推荐的表达方式

在插件中，不建议使用“请登录”作为主要交互词汇，而建议改为：

- 连接云服务
- 导入服务配置
- 粘贴访问令牌
- 启用同步与 AI 建议

这些说法更符合开发者工具的语境，也更符合本项目的气质。

### 3. 登录是否彻底不要

不是彻底不能有，而是：

- 不应是默认首页
- 不应成为使用基础功能的前提
- 如果以后网页端或移动端需要账号体系，可以放在服务层完成
- 插件端只承接最小必要的身份接入

## 六、推荐的模式总览

推荐采用以下总体模式：

### 模式名称

本地优先 + 服务可选 + 自建开放 + 托管收费

### 模式定义

- 插件默认可离线使用
- 云服务仅作为增强能力提供
- 官方提供托管服务
- 同时支持自建服务
- 收费卖的是托管便利与开箱即用体验

### 一句话定位

本地优先，云端可选；支持自建，也提供官方托管。

## 七、能力分层设计

建议将产品能力分成三层。

### 1. 本地基础层

永久免费，且不依赖云端：

- 收藏单词
- 标识符拆词
- 本地建议词库
- 词库管理
- 本地搜索替换
- 导入导出

### 2. 云增强层

通过官方托管或自建服务提供：

- AI 自动分析术语
- 自动生成整体备注建议
- 自动生成拆词备注建议
- 词库云同步
- 跨端数据共享

### 3. 多端体验层

后续逐步扩展：

- 网页端管理
- 移动端复习
- 统一账号或统一服务凭证
- 统一词库资产

## 八、接入方式对比

当前重点讨论三类方式：

- 登录界面
- 订阅链接
- Token / 激活码

### 1. 登录界面模式

优点：

- 常见
- 用户教育成本低
- 容易与网页端统一

缺点：

- 商业感最强
- 对插件来说最“重”
- 容易破坏轻量体验
- 不符合当前产品气质

结论：

不适合作为插件主模式。

### 2. 订阅链接模式

优点：

- 很轻
- 很适合程序员
- 类似 VPN / 代理工具的接入体验
- 便于自建用户接入

缺点：

- 对普通用户仍有一定理解门槛
- 后续如果接入套餐、额度、模型版本、权限控制，单纯链接可能不够稳定
- 链接泄露与过期策略需要单独设计

结论：

适合作为高级模式，或者作为配置分发方式，但不建议作为唯一主入口。

### 3. Token / 激活码模式

优点：

- 足够轻
- 普通用户也能接受
- 便于管理套餐、额度和权限
- 比登录界面克制
- 比纯订阅链接更稳

缺点：

- 首次接入仍需要一步手工操作
- 需要后端提供凭证换取和校验逻辑

结论：

最推荐作为官方托管服务的主接入方式。

## 九、最终推荐的接入模式

### 1. 面向普通用户

官方托管服务使用：

- 官网购买
- 获得激活码或 Access Token
- 在插件中粘贴一次
- 插件自动换取真实配置
- 后续无感使用

### 2. 面向高级用户

插件设置中提供高级配置：

- Base URL
- Access Token
- 服务模式
- 是否启用同步
- 是否启用 AI 建议

### 3. 面向自建用户

支持：

- 自建后端
- 自定义模型接入
- 官方协议兼容
- 最小接入只需 URL + Token

## 十、插件端设置项建议

建议未来在插件设置中增加一个“云服务”分组，而不是单独散落多个配置项。

### 基础设置项

- `termrepoplugin-vscode.cloud.enabled`
- `termrepoplugin-vscode.cloud.mode`
- `termrepoplugin-vscode.cloud.baseUrl`
- `termrepoplugin-vscode.cloud.accessToken`
- `termrepoplugin-vscode.cloud.enableSync`
- `termrepoplugin-vscode.cloud.enableAiSuggestions`

### 建议的模式值

- `off`
- `official`
- `custom`

### 交互建议

- 默认 `off`
- 只有当用户主动启用云能力时，才展开相关配置
- 普通用户优先看到“连接官方云服务”
- 高级用户可展开“自定义服务端”

## 十一、收藏时的 AI 辅助流程

后续最适合优先落地的不是“全局聊天式 AI”，而是“收藏环节的嵌入式 AI 建议”。

### 推荐流程

1. 用户选中单词并执行收藏
2. 插件采集必要信息
3. 若启用了 AI 建议，则调用云端分析
4. 返回整体备注建议与拆词备注建议
5. 将建议内容填充到输入框默认值中
6. 用户确认或微调
7. 保存到本地词库
8. 若启用了同步，则异步上传到云端

### 为什么这样设计

优点：

- 不打断现有流程
- 不会替用户做最终决定
- AI 帮的是“填默认值”，不是“替用户接管”
- 非常符合术语沉淀的使用场景

## 十二、AI 分析接口建议

### 输入建议

不建议只传单词本身，建议传一个最小上下文包：

- `word`
- `languageId`
- `fileName`
- `fileExtension`
- `surroundingCode`
- `filePath`
- `existingSuggestions`

### 输出建议

建议服务端返回：

- `overallNote`
- `parts`
- `part.text`
- `part.note`
- `part.tags`
- `confidence`
- `reason`

### 为什么要返回 confidence

因为 AI 建议并不一定总是准确。

如果后续插件端想做更精细的交互，可以根据置信度决定：

- 是否默认展示
- 是否额外提示用户确认
- 是否回退到本地建议

## 十三、后端应承担的职责

后端不应只是“大模型转发器”，而应承担完整的服务层职责。

### 建议承接的能力

- 用户身份与套餐
- Access Token 管理
- 词库云同步
- AI 术语分析
- 提示词模板管理
- 模型路由
- 限流与额度控制
- 审计日志
- 缓存与降本

### 为什么不能只做“模型转发”

因为后续一旦进入真实使用，就一定会遇到：

- 成本控制
- 高频重复请求
- 模型切换
- 配额管理
- 自建与托管兼容

所以后端要从一开始就按“服务层”去设计，而不只是一个 API 代理。

## 十四、隐私与数据边界

这是该方案能否被用户接受的关键点之一。

### 用户会担心什么

- 私有代码是否被上传
- 公司仓库信息是否泄露
- 代码上下文是否被模型保留
- 词库是否被服务端掌握

### 建议的默认策略

- 默认关闭云分析
- 默认只在用户主动启用时调用云端
- 默认只上传最小必要上下文
- 提供“仅上传单词，不上传代码片段”选项
- 设置中清晰写明数据用途

### 对自建用户的价值

如果你明确支持自建，用户会更容易信任官方方案，因为他们知道：

- 不是被锁死
- 不是必须托管
- 数据流是可理解的

## 十五、开源与商业化边界

### 1. 建议开源的部分

- 插件前端代码
- 后端代码
- 数据协议
- 接口规范
- 自建部署方式

### 2. 建议收费的部分

收费应集中在“官方托管服务”：

- 官方部署
- 官方 AI 调用
- 官方同步服务
- 官方运维与可用性保障
- 简化接入流程

### 3. 核心原则

收费不是为了封锁能力，而是为了提供更省事的体验。

这与开发者群体的价值观更一致，也更容易建立长期信任。

## 十六、与网页端和移动端的关系

后续如果要开发网页端与移动端，建议遵循统一资产层的设计。

### VS Code 插件

负责：

- 收藏
- 编辑器内复用
- 高效沉淀术语

### 网页端

负责：

- 浏览
- 筛选
- 编辑
- 统一管理

### 移动端

负责：

- 复习
- 记忆训练
- 学习节奏跟踪

### 统一后端

负责：

- 词库主数据
- AI 分析
- 同步
- 用户套餐

### 好处

- 数据资产统一
- 客户端职责清晰
- 商业模式也更自然

## 十七、商业化路径建议

### 免费版

- 本地词库
- 基础收藏与管理
- 导入导出
- 本地搜索与替换

### 增强版

- AI 默认备注建议
- 更高质量术语分析

### 专业版

- AI 建议
- 云同步
- 多设备访问
- 网页端管理

### 团队版

- 团队词库
- 共享术语规范
- 审核与协作

注意：以上只是能力层级建议，不代表一开始就要全部实现。

## 十八、近期最推荐的演进顺序

### 第一阶段

先保持插件纯本地模式稳定，继续强化：

- 收藏体验
- 词库管理
- 搜索与替换
- 基础测试

### 第二阶段

先做最有价值的云增强能力：

- 收藏时 AI 默认备注建议

这是最容易让用户感知价值的一步。

### 第三阶段

增加官方托管服务接入：

- Token / 激活码
- 可选云分析

### 第四阶段

增加云同步：

- 跨设备词库同步

### 第五阶段

扩展网页端与移动端：

- 网页端管理
- 移动端复习

## 十九、风险与应对

### 风险 1：产品变重

应对：

- 插件默认不登录
- 云能力默认关闭
- 本地功能完整保留

### 风险 2：商业化引发反感

应对：

- 不封锁基础能力
- 托管与自建并存
- 收费描述聚焦“省事”

### 风险 3：隐私争议

应对：

- 清晰告知数据边界
- 默认最小上传
- 提供自建选项

### 风险 4：系统过早复杂化

应对：

- 按阶段推进
- 先做 AI 建议，再做同步，再做多端
- 不要一开始就把账号、商城、订阅、团队系统全部压上

## 二十、最终建议

综合来看，最适合 TermRepoPlugin 的模式不是传统 SaaS 式的“先登录再使用”，而是：

- 本地优先
- 云增强可选
- 官方托管可付费
- 自建开放可折腾
- 商业化克制且透明

如果用一句话概括未来方向，可以定义为：

> 一个本地优先、云端可选、支持自建、官方提供托管服务的开发者术语资产工具链。

这既保留了项目现在最珍贵的轻量感，也为 AI、同步、网页端、移动端和后续商业化留下了足够清晰的演进路径。
